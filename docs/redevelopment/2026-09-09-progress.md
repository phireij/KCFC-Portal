# KCFC Portal Redevelopment Progress — 2026-09-10

## Branch

`redesign/mobile-first-v2`

Draft PR: #1 — **Redevelopment: mobile-first shell and schedule foundation**

Production `main` remains unchanged.

## Completed in the active redevelopment branch

### 1. Responsive application shell

- New official KCFC navy / royal-blue visual foundation.
- Mobile navigation is exactly five primary destinations: Home, Schedule, Community, Updates, More.
- Horizontal scrolling navigation has been removed from the new shell.
- Desktop uses a persistent left sidebar with role-aware utility and leadership links.
- Mobile More opens as a bottom sheet and contains Availability & Polls, Resources, Inbox, Profile, Accounting when authorized, and Leadership/Admin when authorized.
- Reading-size defaults were normalized toward the approved 15–17 px body range while preserving user-selectable larger accessibility sizes.

### 2. Schedule experience

- Existing detailed duties/assignment page is preserved as `LegacyDuties.tsx` for regression safety.
- `/duties` is a member-oriented Schedule hub.
- **All schedule** shows chronological Mass dates and expandable published ministry rosters.
- **My ministry** shows the member's own liturgical assignments and community duties in one timeline.
- **Plan & manage / Availability & duties** keeps the existing assignment workspace available during migration.
- Legacy notification/deep links containing `tab` or `pollId` still open the detailed workspace.
- Whole-schedule browsing includes:
  - Upcoming / all-date scope controls.
  - Search across Mass title, date, ministry, role and published member names.
  - Quick ministry filters for Lector & Commentator, Ushers and Altar Servers.
  - A dedicated **Where I serve** filter.
  - Clear recovery/reset behavior when filters produce no results.
  - Month-grouped Mass browsing with expandable roster detail.
- My Ministry has separate **Upcoming** and **History** views.
- Published-roster notifications can deep-link directly to `My ministry`.
- A dedicated schedule-browsing UX document records member, mobile, desktop, privacy and future-enhancement rules.

### 3. Home experience

- Existing dashboard is preserved as `LegacyDashboard.tsx` for reference/regression safety.
- Home is member-first rather than admin-statistics-first.
- Home highlights next published assignment, next KCFC Mass, availability-response status, action-needed availability, leadership approval alerts, upcoming Mass dates, announcements and quick links.
- No destructive database actions are present in the new member Home surface.

### 4. Liturgical availability and assignment workflow

- Existing poll implementation is preserved as `LegacyPolls.tsx` for compatibility.
- The redesigned member experience uses member-friendly language centered on **availability to serve**.
- Multi-Mass availability requests remain compatible with existing Firestore poll and response records.
- Members can select every Mass where they are available and revise their response while the request remains active.
- Leader mode includes request creation, response-progress monitoring, availability matrix, assignment builder grouped by Mass/ministry, availability-constrained candidate lists, explicit final roster publication and unpublish.
- New availability cycles use explicit publication state so completed internal planning is no longer treated as member-visible publication.
- Editing an assignment after publication automatically returns the roster to unpublished state, requiring deliberate review and re-publication.
- Final publication creates Portal notifications for assigned members.
- New Schedule surfaces display explicit-publication rosters only; legacy records retain a compatibility fallback so historical schedules do not disappear during migration.

### 5. Community Directory

- Community Directory uses the mobile-first KCFC design language.
- Search, Core/Regular member filtering and multi-ministry filtering are cleaner on phones.
- General directory cards do not expose private member contact details.

### 6. Updates / Announcements

- Updates is rebuilt in the new mobile-first design language.
- Announcement browsing, search, status clarity and editor ergonomics are improved.
- Audience and channel metadata groundwork supports future Public / Parishioner / KCFC Member / Leadership publishing.
- Public website synchronization remains inactive until an explicit production approval gate.

### 7. KCFC Inbox

- Inbox is now treated as the durable source of truth for operational communication.
- Mobile uses a message-list → detail flow rather than squeezing two desktop panes side-by-side.
- Desktop retains a fast split-view experience.
- Search and category filters cover announcements, duties, broadcasts and system messages.
- Unread counts and Mark All Read remain available.
- Messages support deep links back to their relevant Portal workflow.
- New routing metadata can show urgency, source type and delivery channels while older notification records remain compatible.

### 8. Profile, communication preferences and notification health

- Profile is rebuilt in the approved visual language.
- General private profile fields remain editable without exposing them in the public member directory.
- Communication preferences now distinguish announcements, liturgical availability, published assignments, community duties, broadcasts and urgent notices.
- Email is represented as the default partner to PWA push.
- New App & Notification Status surface shows:
  - installed-browser vs standalone app state,
  - browser notification permission,
  - registered push endpoint count,
  - healthy / setup-needed / blocked / repair-needed state,
  - one-tap enable or repair registration action.
- Channel overview communicates KCFC Inbox → PWA → Email → optional LINE / Telegram → future WhatsApp hierarchy.
- Optional messaging apps remain non-mandatory.

### 9. Communications architecture

`communication-routing-and-notification-health.md` records the approved routing model:

1. KCFC Inbox as durable source of truth.
2. PWA/Web Push as primary alert channel.
3. Email as default partner.
4. LINE as first optional Japan-focused secondary connector.
5. Telegram as another optional connector.
6. WhatsApp future/conditional pending implementation validation.
7. Viber low priority.
8. SMS optional paid escalation only.

Type definitions now support backward-compatible routing metadata, delivery diagnostics, optional connected-app records and explicit user communication preferences.

## Data handling

The redevelopment continues to use existing Firebase Auth identities and current Firestore records. No user recreation or destructive migration is introduced.

Current compatibility sources:

- `users`
- `polls`
- `polls/{pollId}/responses`
- `duties`
- `announcements`
- `notifications`

All new communication fields are optional so historical Firestore documents remain readable.
